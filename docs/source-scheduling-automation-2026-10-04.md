# Source scheduling automation — coverage, locking, real-collector trial and failure handling (4 October 2026)

Branch `codex/vacancy-growth`. Nothing here is deployed. **No production schedule is enabled**: `SOURCE_SCHEDULE_ENABLED` stays off unless a deployment sets it, and every source also needs `scheduled=true`. The scheduler tests use synthetic in-process collectors, a disposable Postgres database and a private Redis prefix. The one exception is the acquisition trial (section 6), which contacted two live public sources with a handful of requests, from an isolated database copy; its evidence is kept apart from the synthetic tests everywhere below. No e-mail, candidate matching or application was involved.

## 2. One source lease for every way of collecting
Before: the scheduler held a lease, but the manual import CLI did not, so a manual import could overlap a scheduled run. Now **one lease per source** (`JobSource.leaseOwner/leaseUntil/leaseHeartbeatAt`, `jobs/source-lease.service.ts`) is taken by all three holders: `scheduler`, `operator` (run-now) and `cli` (manual import). The lease has a secret owner token (`<holder>:<random>`), a 45-minute TTL, is renewed by a heartbeat while collection works, and is released (or recovered) by compare-and-set on the token.

* **Enforced on the server, not by convention.** The internal import routes for the reviewed collector sources (`ingest`, `confirm-listed`, `import-runs`) require the caller's token in `x-source-lease` and answer 409 without a live matching lease; a run whose lease was taken over aborts (`LeaseLostError`) and neither records nor closes anything, and only the current owner settles the source. So an ordinary import path that skips locking no longer exists for those sources.
* **Manual import CLI**: with `--apply` it acquires the lease (`POST internal/jobs/source-lease`), renews it, releases it in `finally`, and reports a refusal clearly ("source is held by scheduler"). Without `--apply` it only previews and writes nothing. `--skip-known` fetches the stored ids (`GET internal/jobs/known-ids`) for a cheap resume.
* **Tested** (`source-lease.e2e-spec`, `source-automation.e2e-spec`): manual vs scheduled overlap in both directions, operator vs scheduler, lease renewal during a long run, takeover after expiry, crash recovery (CAS, one winner), a stale holder unable to write or release, and routes refusing writes without the token.

## 3. Durable coverage of large boards
A job board is far larger than one bounded run (a run is 4–12 pages / 80–200 details). Three kinds of run share the work and never confuse each other's authority (`jobs/source-discovery.ts`, stored in `SourceDiscoveryProgress`):

* **Head refresh** (incremental, or reconciliation until a verified-complete listing exists): from the first page, cheap, at the source's interval. The only kind that can walk a whole listing in one run, so the only kind a closure can come from.
* **Deep segments**: continue a stored traversal (`cursor`: page number, API cursor, next listing URL or a queue of shards, depending on the collector) so successive bounded runs go beyond the same head pages. Segments are spaced at least six hours apart and a new traversal starts weekly. A resumed segment is always recorded as a segment (`closureSkipped = resumed_segment`) and **can never close anything**, even if a buggy collector claims a complete listing (tested). An interrupted segment (crash, lease lost, hard error) stores nothing: the cursor stays where it was.
* **Revalidation**: stored active postings whose detail page was last fetched more than 14 days ago are fetched again, oldest first, a few per run (10 / 20 / 25 by run kind, never more than a quarter of the run's job budget) instead of being skipped as "known" for ever. Unchanged ones just refresh their time; changed ones update and re-match as usual.

**Shifting listings.** A page number alone is not trusted. Positional cursors resume one page earlier than they stopped, every segment stores the last ten postings it saw (`anchors`), and the next resumed segment must see at least one of them among the postings it reads; if not, the listing moved under the cursor and the traversal restarts, with the reason recorded (`listing_shifted`) and shown. Tested for postings added at the head (absorbed by the overlap), a large addition and postings removed ahead of the cursor (both detected).

**Closures** still happen only inside `recordRun`, from one verified-complete run: a posting must be absent from two such listings, and a listing that shrank below half or arrived out of order closes nothing. A large board that never fits one run therefore never closes anything: that is deliberate (limit, section 8).

### Defects the real-collector trial found (all fixed, each with a mutation-checked regression test)
1. **Postings whose own detail page never validates made a source fail for ever.** Work.az had three head postings that the parser rejects every time; each run counted as a failure, so the discovery cursor was never stored and the source would have entered cooldown after five runs. Now a small share (≤ 10 %) of content-only detail failures is tolerated: the run is healthy and keeps its progress, stays incomplete (nothing closed from it), and names the postings in the run summary/log (`failedDetails`). Transport failures (429, 403, timeouts) and a large share of bad pages still fail the run.
2. **The resume continuity check only looked at the first 40 postings of the resumed page**, but real pages hold about 50 and the anchors sit at the end of the previous one: every resume was judged "listing shifted" and the traversal restarted for ever, never going deeper. The check now looks at everything the segment read.
3. **Revalidation could consume a small job budget** and keep the cursor on one page. Its share is capped at a quarter of the budget.
The synthetic tests had passed before these were found: the board model used five postings per page and no permanently bad posting. Both are now in the tests (real page size, unparseable postings).

## 4. Failure handling: durable cooldown, admin status, recovery, alerting
* **Failure counts and backoff.** A failed run backs off exponentially (capped at 7 days). **At 5 consecutive failures, or on the first classification of BLOCKED (403/429/captcha), the source enters a durable cooldown** (`cooldownUntil`, `cooldownReason`, `cooldownCount`): 24 hours, doubling per repeat up to 7 days. Nothing claims a cooling-down source, scheduled or run-now (409). After it ends one probe run is allowed; success clears everything, failure escalates.
* **Clear admin status.** `/admin/sources` shows `COOLING_DOWN` with the reason, the end time and the number of times, in Azerbaijani, with "Bərpa et" (recover) and "Bərpa et və işlət" (recover and run now) buttons; the cooldown also appears in the recommended actions.
* **Recovery path.** `POST /admin/ops/sources/:key/recover` (needs `ops.control`, audited as `SOURCE_COOLDOWN_RESET`) clears the cooldown, the failure count and the backoff so the source is due again; with `run: true` it also starts a run at once (same lease and checks as run-now). It never touches a lease: an abandoned one is recovered by the next tick, a live one keeps the source busy.
* **Alerting — honest status.** The only existing alert surface is the in-app recommended-actions list and the structured error log (`source_cooldown_started`). **No outbound operator channel (e-mail, chat, pager, webhook) is configured or used**, so a cooldown reaches a person only if someone opens the admin or reads logs. Adding an outbound alert needs a decision and credentials from the founder (a destination address/webhook and permission to send to it); nothing was sent or wired. Until then a deployment should watch for `source_cooldown_started` in its logs.

## 5. How a scheduled run behaves (summary)
One source per tick (every 10 minutes; `SOURCE_SCHEDULE_TICK_PATTERN` may set `*/N * * * *`, N = 1–59, used by the trial), claimed by the lease; a source with no reviewed collector, `RESTRICTED`, disabled, paused, cooling down or Glorri is never claimed. Employer feeds and ATS tenants use the employer budget (5 pages / 150 details / 1.5 s) and are read completely each run; job boards use head budgets (4 pages / 80 details incremental, 12 / 200 reconciliation) and deep budgets (12 pages / 120 details). No budget is faster than 1.5 s per request. Stored postings are confirmed as listed in batches rather than fetched again. The repeating tick is registered exactly once however often the API restarts and removed when the schedule is off.

Operator controls (`ops.control`; SUPPORT is read-only): `POST /admin/ops/sources/:key/run-now` (202, same lease), `…/recover`, `PUT …/schedule` (pause/resume, interval), and the global `import.scheduled` switch (`PUT /admin/ops/scheduler/pause` is an alias). `/admin/sources` shows the operational status, recommended action, discovery progress and these controls.

## 6. Real-collector acquisition trial (live sources, isolated copy)
**What this is.** Two enabled, eligible, real collectors — **Work.az** (a large board; its public API and pages) and **Xsolla** (a Lever ATS feed) — ran through the **real scheduler** (BullMQ repeating tick every minute → processor → `SourceScheduler` → real collector → real ingestion → run recording → discovery progress) in a child process, against `aise_sched_trial_<n>`, a **disposable copy of the isolated acquisition database** (`aise_census_growth_test`; dropped afterwards, the original untouched; no other source was scheduled; Glorri is never claimed). **No import command was run by anyone**; the driver only prepared the copy, started and killed the scheduler process and read the database. Re-runnable: `apps/api/test/scheduler-acquisition-trial.ts` (+ `test/support/scheduler-trial-app.ts`); logs and the result JSON are kept outside Git in `~/aise-preview/trial/`.

**What is conservative.** Budgets clamped per run to 3 pages, 40 details (150 for Xsolla: one request returns the whole feed), at least 2.5 s between requests; the only reachable hosts are the sources under test (everything else is refused in-process); the matching queue is a stub, so nothing is matched or sent; request metadata (host, path, status, no bodies) is logged. **83 requests in about 6.5 minutes**: 68 `www.work.az`, 9 `api.work.az`, 6 `api.lever.co` (all HTTP 200, robots.txt read first).

**What is compressed or staged (so the evidence is not over-read).** Time: between steps the driver moves due times in the copy (`nextRunAt`, `lastHeadAt`, `lastSegmentAt`, lease expiry) instead of waiting hours; the lease-recovery code is the real one, only its 45-minute clock was moved. Revalidation: the copy's 850 stored postings of these sources were aged to 20 days so the 14-day rule had work. New postings: the copy already held the head of Work.az, so the 12 newest Work.az postings were deleted from the **copy** to show discovery of postings new to the database (they were not new to the source).

| Step | Work.az | Xsolla |
|---|---|---|
| Cycle 1 (head, reconciliation) | 3 pages, 150 listed, **12 new**, 1 updated, 134 confirmed, **3 failed** (unparseable pages), 10 revalidated (1 changed); cursor → page 4 | 178 in feed, 38 in scope, all unchanged (refreshed by upsert), 0 failed |
| Cycle 2 (deep segment resumed from the stored cursor) | 3 pages, 150 listed, 0 new, 150 confirmed, 20 revalidated (0 changed), 0 failed; cursor 4 → **6**, 300 listed in this traversal | same, 0 new / 38 unchanged |
| Third run, **SIGKILL** of the scheduler process mid-run | run row left `RUNNING`, lease held; nothing stored: cursor still 6 | — |
| **Restart** (new process, no manual command) | lease recovered, the run marked `FAILED` ("terminated or lease expired", 1 failure counted), then a deep segment resumed from the stored cursor: 3 pages, 20 revalidated, **cursor 6 → 8**, 450 listed in this traversal, restart reason none | ran again: 38 unchanged |

Totals across the seven runs: new **12**, refreshed **50** Work.az postings by revalidation (1 changed) plus all 38 Xsolla postings on each of its three runs (unchanged), failed **3** unparseable Work.az pages in the head run and **1** killed run, duplicates linked **0**, closures **0** (no run was complete; that is by design). Actual coverage progress: the Work.az traversal advanced from the head to page 8 (about 450 of its postings listed) across a crash and a restart; it was **not** completed, and the board is not proven complete. Cooldown was not triggered live (no repeated failure occurred); it is covered by the synthetic tests only.

**What this evidence does and does not show.** It shows that the real scheduler, real collectors and the durable state work together over repeated cycles, across a hard kill and a restart, and it found three defects (section 3) that the synthetic tests had not. It does not show steady-state behaviour over days, behaviour of the other sources, or that the sources permit scheduled collection (terms are unreviewed).

## 8. Limits and not done
* **Large boards never close postings.** A board that does not fit one run (Work.az, HelloJob, Boss, SmartJob) has no run that can prove completeness, so its postings stay open until their deadline or a manual decision; closure needs a board that fits a head run, or an item-anchored full traversal designed to prove completeness (not built).
* Content-only failures are only recognised for collectors that report them (`onFailedDetail`: Work.az and the manual CLI path today); other collectors count them as failures as before, conservatively.
* The same unparseable postings are fetched again on every run (about three requests); there is no per-posting retry back-off.
* ATS and employer collectors (Lever, Workable, …) have no discovery cursor: their feed carries the full detail, so each run refreshes everything and revalidation does not apply.
* JobSearch (a single listing) has no persisted cursor.
* No outbound alert channel (section 4). The cooldown surface is the admin and logs.
* The trial exercised **two** real sources briefly with compressed time and clamped budgets; the other collectors (HelloJob, Boss, SmartJob, eJob, JobSearch and the employer tenants) were not run live under the scheduler. All sources remain `ROBOTS_ALLOWED_TERMS_PENDING`: terms of use are not reviewed, so no production schedule should be enabled before that review.
* Production deployment, production schedules and live application e-mail were not touched.

## 9. Census reporting excludes expired vacancies
The previous report counted postings whose deadline had passed as actionable (2,679). The backend predicate is `status='ACTIVE' AND hiddenAt IS NULL AND duplicateOfId IS NULL AND (deadline IS NULL OR deadline >= now)`. The corrected report (`vacancy-growth-census-report-2026-10-04.md`) was verified read-only against the database: 2,727 stored, 869 expired, **1,818 open unique unexpired**, 314 with an e-mail application route, 192 verified in complete listings, 1,626 freshness unknown, 48 duplicates. A test pins that open, e-mail and verified counts exclude expired, duplicate and hidden postings.
