# Scraper patch review and integration (3 October 2026)

Baseline: branch `codex/vacancy-email-applications`, head `0fe694aebc829ad85877e7c7360dc04ffa7abd70` (CI green on that exact SHA, both runs). The ChatGPT proposals were treated as **untrusted**: nothing was executed from the archives, the original/enhanced ZIPs were extracted only into a temporary directory outside the repository (never over it), and the patch was applied to the repository only after being read in full and compared with the original package (original == repository for every touched file, so no credential placeholder could replace real configuration). Source websites' headline counts below are quoted as source claims, never as AISE inventory.

## 1. What the patch contained, and the verdict for each part

| Part | Verdict | Why (evidence) |
|---|---|---|
| eJob parser + collector (new) | **Accepted in concept, rewritten** | The shipped version could not work on the real site: (1) it read robots.txt with the repository's fail-closed parser, which refuses the `Crawl-delay` directive that ejob.az's robots.txt contains, so the first request always aborted; (2) it parsed the publication date as `DD-MM-YYYY`, but the page prints ISO `YYYY-MM-DD` (and carries a `JobPosting` JSON-LD block) so every real detail would have been rejected; (3) employer came from a loose `[class*="company"]` selector instead of the real structure. Tests used synthetic robots (`Allow: /`) and a made-up date format, so they never exposed any of this. |
| JobSearch classic parser + collector (new) | **Accepted in concept, rewritten** | robots.txt asks `Crawl-delay: 30` for every crawler (same fail-closed abort); the listing's publication evidence was taken from the link's own `<li>`, but the real "Published"/"Deadline" columns are sibling cells, so **every real entry would have been rejected** (`relativePublished` null). Real listing cards carry explicit day/month columns, which the rewrite uses. Pacing of 1 s would have violated the stated 30 s. |
| Work.az: start at `/aktiv-vakansiyalar`, allow `/is-elanlari` | **Rejected** | Live check (2026-10-03, robots allows): `/aktiv-vakansiyalar` returns exactly the same 12 vacancy links in the same order as `/vakansiyalar` (the rest is a client-side "Daha çox yüklə" button), so the change adds nothing; it broke 3 existing Work tests; `/is-elanlari` was allowed but never used. |
| Work.az: rendered-text fallback when JSON-LD is missing | **Rejected for now** | All three sampled detail pages (two current, one expired) carry a complete `JobPosting` JSON-LD block, so the claim that current pages lack it is not supported. The fallback parses flattened page text with regexes (location `[^#]+?`, employer from "the element after the title") that were validated only against one synthetic fixture. Missing or malformed content must be rejected, not recovered from unverified text; revisit only with a real JSON-LD-less page as evidence. |
| Migration `20261013090000_register_ejob_jobsearch` | **Accepted, corrected** | Renamed to `20261014090000_…` (the original timestamp sorted *before* already-applied migrations); access review set to `ROBOTS_ALLOWED_TERMS_PENDING` with the facts actually verified; scheduling stays off. Upgrade-tested on a disposable database (see §4). |
| Collector registration | **Accepted** | One list serves the CLI and the scheduler. |
| `docs/scraper-review-2026-10-03.md` | **Rejected** | Contained unmeasured claims (≈7,941 / 2,068 / 1,799 headline counts used to argue coverage, "tests pass" for suites that were never run). Replaced by this document. |
| "Verification actually executed" claims | **Not reproduced** | The package author could not run Jest; when the shipped specs were run here, **5 failed** (2 JobSearch, 3 Work). |

## 2. What was added or changed (all additive; existing collectors untouched)

- `public-job-collector.ts`: `Crawl-delay` is now parseable **only** by a collector that declares it enforces it (`robotsAllows(text, path, { crawlDelayHonored: true })`); everyone else still fails closed as before (the existing test for that stays and passes). New `robotsCrawlDelayMs()` returns the delay that applies to our own agent (a delay addressed only to other crawlers, such as eJob's AI-bot groups, does not apply to us).
- `baku-time.ts` (new): Baku (UTC+4) calendar handling. A date-only start is the start of that day in Baku; a date-only **deadline is the end of that day**; zone-less date-times are Baku local (the shared `parseStrictIsoDate` reads them in the *machine's* timezone, which the new code avoids); impossible dates are `undefined`; day/month values without a year get the year that makes a publication date real, recent and not in the future.
- eJob and JobSearch parsers/collectors (rewritten, see §3) and registration migration `20261014090000_register_ejob_jobsearch`.
- `work.parser.ts`, `smartjob.parser.ts`, `boss.parser.ts`: date-only deadlines are the end of that day in Baku (was UTC midnight, i.e. four hours into the stated last day).
- Tests: `baku-time.spec.ts` (8), crawl-delay cases in `public-job-collector.spec.ts`, `ejob.collector.spec.ts` and `jobsearch.collector.spec.ts` (fixtures follow the structures observed live; no third-party text), three dedup regression cases in `job-dedup.util.spec.ts`, and `test/new-public-sources.e2e-spec.ts` (new collectors → real guarded ingestion route, validation, dedup link, moderation, failed/incomplete runs closing nothing, expiry) on the isolated database.

## 3. Behaviour of the two new collectors

| Concern | eJob (`ejob`) | JobSearch classic (`jobsearch`) |
|---|---|---|
| Entry points | `/is-elanlari/`, `/is-elanlari/page-N/` (60 pages observed), details `/is-elani/<id>-<slug>/` | `/vacancies?hl=az` (latest ~200 cards, no proven pagination), details `/vacancies/<slug>-<id>` |
| Identity | `ejob:<numeric id>` (must also equal the JSON-LD identifier) | `jobsearch:<numeric id>` (card id must equal URL suffix) |
| Employer | JSON-LD `hiringOrganization`, cross-checked with the visible `.name`; disagreement → rejected | card employer cross-checked with detail; disagreement → rejected |
| Location | JSON-LD place (foreign country/locality rejected), else the labelled city; not stated → country-level `Azerbaijan`, flagged `locationKnown:false` | not on the page → `Azerbaijan`, flagged unknown |
| Publication date | JSON-LD `datePosted` (ISO) else `Əlavə olunub : YYYY-MM-DD`; missing/invalid → rejected | listing "Published" column (day/month, year inferred as a real recent non-future date); a card without both date cells is ambiguous → rejected |
| Deadline | JSON-LD `validThrough` (zone-less = Baku; date-only = end of day). Observed values are mostly ~5 months out and look platform-generated, so they are labelled `source_valid_through`, not an employer deadline | detail "Deadline D Month YYYY" (full date), else the listing column; none → unknown |
| Application contact | contact details are an image/message form → no address unless the vacancy **text** states one; chrome/support/complaint addresses never enter the description | the address is filled in by script and is not read; nothing invented |
| Query parameters | dropped (the path is the identity; none observed to matter) | only `hl` kept |
| Pacing / access | robots read first; paced ≥ 5 s (eJob's robots asks AI crawlers for 5 s; kept as our floor) and never below a crawl-delay that applies to us; redirects only to approved paths; 403/429/blocks stop the run, no retry | paced at the file's `Crawl-delay: 30`; same stop rules |
| Completeness | **never `complete`**: featured entries repeat on every page and the site's own counts disagree, so a full walk does not prove an active census | **never `complete`**: bounded recent snapshot |
| Closure | none possible from these sources until a verified complete run exists | none possible |
| Scheduling | `scheduled=false`, `ROBOTS_ALLOWED_TERMS_PENDING` (terms/attribution **not** reviewed; robots permission is not republication approval) | same |

Deduplication is unchanged and conservative: a JobSearch posting with no city links to an eJob posting only when company, title, publication day and text are essentially identical; different cities, different text, different day or a different role at the same employer stay separate (regression tests).

## 6. Remaining bugs, risks and next steps
**Bugs and risks that remain (nothing here was changed beyond what is listed above):**
1. The date-only-deadline-as-UTC-midnight defect (a posting stated to close on 4 October was treated as expired from 04:00 Baku on 4 October) existed in the Work.az, Smartjob and Boss parsers. All three now use `bakuInstant(value, 'end')` with regression tests. The other collectors were read for the same defect: ABB, hellojob, Yelo and SAP already convert to the end of the Baku day; PwC states no deadline (rejects one it does not understand); Workable and Teamtailor carry no deadline field. No further change was needed.
2. The shared `parseStrictIsoDate` reads zone-less date-times in the *machine's* timezone. New code avoids it; the older collectors that still use it for zone-less values should be moved to `bakuInstant`.
3. Work.az discovery reaches only 12 active postings per fetch. Finding the real "load more" request is a discovery task that needs a source-terms/robots review first; it must not be reverse-engineered around access controls.
4. eJob and JobSearch location: JobSearch gives no location in static HTML and eJob sometimes none; the country-level fallback is flagged `locationKnown:false` in the payload but the DTO has no field for it, so catalogue filters by city will not see these postings under a city.
5. eJob `validThrough` is used as the deadline (it is the source's stated validity end); if the owner decides it is only a platform auto-renew date it should be dropped from the deadline and kept as payload only.
6. Neither new source has been terms/attribution reviewed (`ROBOTS_ALLOWED_TERMS_PENDING`); scheduling is off and must stay off until that review.

**Next steps (in order):** (1) owner review of terms/attribution for eJob and JobSearch; (2) staging import of a *small* bounded batch through `npm run script:import-public-jobs -- --source ejob --apply` into a non-production API with the source-coverage report to measure duplicate-linked and uniquely actionable counts; (4) only after a verified complete eJob listing walk (60 pages ≈ 5 minutes at 5 s plus details) and a headline reconciliation, consider allowing `complete` for eJob so closures can run through the existing consecutive-complete-run safeguards.

**Commands.** Preview (read-only, no ingestion): from `apps/api`, `npx ts-node -r tsconfig-paths/register src/scripts/import-public-jobs.ts --source <ejob|jobsearch|work> --max-pages N --max-jobs M --delay-ms D` (the new collectors raise the delay to their robots/floor value by themselves). Tests: `npx jest src/scrapers/public-jobs src/jobs/job-dedup.util.spec.ts`; integration: `DATABASE_URL=<aise_phase2_test> npx jest --config ./test/jest-e2e.json --runInBand --forceExit new-public-sources public-job-import source-registry source-scheduler`.

## 7. Isolated import trial (session 5) — real ingestion path, disposable database
Access position first: see `docs/source-access-and-attribution-2026-10-03.md`. Neither eJob nor JobSearch publishes terms that permit reuse; migration `20261015090000_hold_ejob_jobsearch_pending_permission` disables both so the ingestion API refuses them in any environment that applies it (e2e-proven). The trial therefore enabled them **only inside a database the script created and dropped** (`test/source-import-trial.ts`: create scratch DB → `prisma migrate deploy` → real guarded ingestion route with DTO validation → measure → drop). Matching queue was a stub and no mailer exists in that module, so no notification or application message could be sent. Sequential, ≤ 50 details per source, collectors' own pacing (eJob 5 s, JobSearch 30 s crawl-delay, Work.az 1.5 s), 36 minutes in total, no blocking response. The page content was kept in a scratch file outside the repository (not committed).

| Source | Details fetched | Accepted & stored | Rejected | Failed (transport) | Expired | Created / unchanged on first run |
|---|---|---|---|---|---|---|
| Work.az (existing) | 12 (all it can reach) | 12 | 0 | 0 | 0 | 12 / 0 |
| eJob | 50 (listing: 61 distinct entries over 2 pages) | 49 (+1 after the fix below) | 1 | 0 | 0 | 49 / 0 |
| JobSearch classic | 50 (listing: 200 cards) | 50 | 0 | 0 | 0 | 50 / 0 |
| **Total** | 112 | **111** | 1 | 0 | 0 | 111 / 0 |

**The one rejection was a real bug in this work, now fixed:** eJob leaves HTML entities inside its JSON-LD strings (`&quot;Kitchen Plus&quot; restoranı`); the cross-check against the visible employer name called a legitimate posting inconsistent. Structured strings are now entity-decoded (stored as `"Kitchen Plus" restoranı`), with a regression test; the real page parses. No stored record in the trial contained an undecoded entity.

**Deduplication:** 0 duplicate links within sources, 0 across sources; 0 same-source repeats of company+title+location. Distinct employers: 73 in 111 records (Work 5, eJob 27, JobSearch 41); **no employer appears in more than one source** in this sample, so the three sources look largely disjoint (small sample; low confidence). Overlap with AISE's *existing* open inventory (1,426 open unique on 2026-10-02, `docs/source-integration-and-census-2026-10-02.md`) was **not measurable** locally (the development database is not migrated and the trial database starts empty); that needs a staging import.

**Unique actionable (open, not hidden, not a duplicate, deadline not passed):** 111 of 111 — but see freshness: this count is "not known to be closed", not "known to be open".

**Freshness — publication dates and platform deadlines validated separately**
- *Publication dates* (Baku calendar): Work 4 Sep–3 Oct (10 of 12 within 7 days), eJob 30 Sep–3 Oct, JobSearch 2–3 Oct; 0 future dates, 0 publication-after-deadline, 100% of JobSearch years are inferred from the listing's day/month (flagged in the payload). **17 of 49 eJob postings carry ids more than 3,000 below the newest while showing a publication date within the last four days: eJob re-publishes/bumps older ads**, so a recent publication date is not proof of a new vacancy and same-source reposts are not linked (by design).
- *Deadlines:* eJob `validThrough` is **exactly 150 days after publication for 49/49**, JobSearch's deadline is **exactly 32 days for 50/50**, Work.az's is 30 days for 83 % (range 12–30). These are platform default windows, not employer statements. **All 111 actionable postings are therefore "unknown freshness"**: the only evidence is a recent publication date and a platform window; a fetched page does not prove an employer still accepts applications.
- *Application destinations:* every record has the original posting link (0 missing); stored method `EXTERNAL_SITE` for 110, `EMAIL` for 1 (Work, stated in the vacancy text). eJob and JobSearch expose no application address in static HTML, so their real apply route is unknown beyond "open the original page". *Employers:* 0 missing among stored (postings without an employer are rejected, never invented). *Locations:* JobSearch 50/50 unknown (country-level fallback), eJob 0/49 unknown, Work 0/12.

**Idempotency:** replaying all 111 accepted records through the real ingestion route: 111 unchanged, 0 created/updated, same row ids, 0 changed content hashes, row count 111 → 111. A fresh live re-collection (eJob 8, Work 4, JobSearch 4 details): 16/16 unchanged, still 111 rows.
**Moderation and references:** a hidden posting with a saved-job reference was re-ingested: same row, still hidden with its reason, reference kept, outcome `unchanged`.
**Closure safety:** 60 import-run reports (5 kinds — limit reached, parse failures, `complete:true` with failures, `complete:true` with a 429 error, empty listing — × 4 repeats × the 3 sources) closed **0** postings and left every row's status and miss counter unchanged. A control source with verified-complete listings closed only its own missing posting after the documented two consecutive misses (closed counts per run 0,1,0,0); the other sources' rows were untouched. **Complete-run closure was not enabled for eJob/JobSearch/Work** (their collectors cannot report `complete`).

**Incremental inventory:** the two new sources contributed 99 stored, nominally actionable postings in this bounded trial (Work's 12 were already an existing source). Reachable per-run stock with the current collectors, if permission were granted: eJob up to ~60 listing pages (≈ 1,800 listed on the site's own pagination, unverified census; ≈ 2.5 hours of detail fetching at 5 s), JobSearch ≈ 200 cards per listing (≈ 100 minutes at 30 s), Work.az 12. Site headline counts are not AISE inventory and nothing here supports a claim near 5,000.

**Remaining coverage bottlenecks:** (1) permission for eJob/JobSearch (blocks 100 % of their use); (2) Work.az's active listing is cut off at 12 by a client-side "load more" request the collector does not issue; its sitemap is entirely stale; (3) freshness: none of these sources gives employer-stated deadlines, so "still open" cannot be proven from a fetch — re-fetch recency and source presence in a *verified complete* listing are the only signals, and no complete listing exists; (4) JobSearch's 30 s crawl-delay caps it at ~120 details per hour; (5) overlap with existing inventory is unmeasured.

**Next highest-value acquisition step:** *Work.az pagination*, because Work.az is already registered with robots allowing the paths, its first page shows a different order of magnitude than we reach (12 vs a claimed ~7,900 active), and it needs no new permission decision beyond the existing pending review. Read the listing page's own public client script (read-only, no login, no access-control circumvention) to learn the "Daha çox yüklə" request contract; implement bounded pagination in the existing collector with the same safeguards (paced, stop on any restriction, never `complete`), then repeat this trial with ≤ 50 details. In parallel, send the written permission request in §"What is needed from the owners" of the access document to eJob and JobSearch; until a reply exists their collectors stay disabled.
