# Azerbaijani writing guidance for motivation letters — what changed, and what is not claimed (4 October 2026)

Scope: the **motivation-letter** pipeline only (`ResumeTailorService.generateLetter` → `reconcileLetter`). CV and resume generation, their prompts and their checks are unchanged (a test pins this). The AI engineer's guidance was adapted into the product's own wording; it was not pasted. The engineer's separate CV tool (`ats-harvard-resume`) was read only to look for letter rules (there are none); nothing from it was copied.

## 1. Prompt changes (code and wording; **no model quality is claimed by any of this**)
`src/resumes/tailor/letter-style.ts` builds the system prompt; the user message keeps its shape (`persona`, `candidate_motivation`, `job`, optional `fixed_paragraphs`, plus `question` in answer mode) and the output stays `{"paragraphs":[...]}`, so paragraph ids, approval snapshots, language selection, allowances and attachments are unaffected.

* **Voice and style (all languages):** first person, plain professional wording, direct verbs and concrete actions; pick one or two relevant experiences or stories and say how they connect to the vacancy; mention a tool only where it explains the work; no list of skills; avoid translated-sounding or inflated wording, sentences that fit any employer, repeated connectors and "not X but Y" contrasts (at most one); light punctuation (no dash-separated asides, at most one colon). **No blanket hyphen ban:** names, dates, e-mail addresses and URLs stay as written (a test pins this).
* **Azerbaijani wording block (az letters only):** preferences taken from the engineer's guidance (e.g. "təbii", "uyğun gəlir / maraqlı gəlir", "aydın oldu", "canlı / əsl / konkret" rather than "real" as an adjective, plain finite verbs, name the action instead of "bunu etmək", finish every sentence). These lexical choices are the engineer's judgement; **they have not been verified by an independent Azerbaijani reader**. The engineer's "keep the human line / add a small personal contradiction" advice was deliberately **not** adopted: it conflicts with the factual boundary below.
* **Factual boundaries:** candidate facts come only from confirmed profile evidence, stories and the candidate's own answers; no invented enthusiasm, preferences, feelings, difficulties, metrics, responsibilities or achievements; a feeling is allowed only if the candidate's own text states it. Vacancy information explains the role and company and is never a claim about the candidate. With no stated reason for the company, **no admiration**: one modest sentence tying something the candidate did to what the vacancy asks.
* **Untrusted input:** persona, motivation, job and (in answer mode) the question are declared data, not instructions, in the system prompt; the question text appears only in the user message (tested with an embedded "ignore all rules").
* **Two output modes:** `letter` (3–4 short paragraphs, room for one or two pieces of evidence, the existing behaviour) and `answer` (a short answer to an application question: two plain paragraphs, about 110–200 words, or the destination's own limit via `maxWords`). `answer` is a service-level option only: **no new API route and no new document kind were added**; the letter documents the API produces still use `letter`.

## 2. Code-side checks added (letters only; focused tests in `tailor-facts.spec.ts` / `resume-tailor.service.spec.ts`)
* **Invented personal statements:** a sentence with a strong feeling, taste, hardship or dream marker (az / en / ru / tr lists) is removed as `unsupported_personal_claim` (error, shown to the candidate) unless the candidate's own text (profile, stories, motivation) uses the same word; the vacancy text cannot supply it. Plain interest in the vacancy is not removed.
* **Unsupported metrics / employers / tools:** unchanged generic checks, plus one narrow gap closed for letters: a sentence **opening** with an unmentioned organisation name followed by an organisation word ("Amazon şirkətində …") had no capital-letter tell-tale and passed; it is now removed.
* **Skill dumping:** a sentence naming four or more of the candidate's own skills is kept (they are facts) but flagged `skill_list` (warning).
* **Short answers:** `answer_length` (warning) when the fact-checked text is outside 110–200 words (or above `maxWords`).
* **Approved content:** approved paragraphs are kept word for word at their position on regeneration even if they would not pass these checks (tested); the model is told they are fixed.
* The web review screen has Azerbaijani labels for the three new issue codes.
Not changed: allowances, snapshots, e-mail attachment hashes, approval flow.

## 3. What was run
Unit: `src/resumes` (6 suites, **127 tests**, including the new ones) pass; API build typecheck and web typecheck clean; `test/documents.e2e-spec.ts` (20 tests, letters through the real queue, with the deterministic fake provider) passes. No full suite repeated. The local preview was restarted so it runs the new prompt (still the fake provider; a fake letter now shows the `skill_list` note because it lists the candidate's skills in one sentence).

## 4. Real-model evaluation: prepared, **not run, no result**
_Superseded in scope the same day: the evaluation is now a before/after comparison with more cases (budget 3 requests per generation); see `cv-resume-guidance-and-letter-guards-2026-10-04.md`. The statements below about flags and independent review still hold._

`apps/api/test/evals/` now covers 11 generations: Azerbaijani, English and Russian × resume / CV / letter, plus **two Azerbaijani short answers** (one with the candidate's own reason for the company, one without; the second must show no invented admiration). Budget `EVAL_MAX_CALLS` default 33. Still blocked: no `NVIDIA_API_KEY` here; the harness refuses a loopback (fake) endpoint.
For the letters and answers it records mechanical flags (personal claims that survived the guard, skill-dump sentences, word count, admiration without a stated reason, and for Azerbaijani the engineer's banned-wording and repetition flags such as "doğal", "real" as an adjective, a repeated "X yox Y", several sentences starting with the same connector, an unfinished sentence). **These flags cannot establish naturalness, and keyword or fake-provider output cannot establish writing quality.**
It also writes `az-review-sheet.md`: every Azerbaijani letter/answer under a neutral id in a fixed pseudo-random order, with no scores, flags, model or provider names, and a short form (natural or translated-sounding with quoted phrases; anything invented; tool list; would send under own name). The id→source key is a separate file. The reviewer must be a native Azerbaijani reader independent of the guidance author and of the developers. Until that sheet is filled in and the PDFs are read, **there is no writing-quality result**.
The harness mechanics (answer mode, flags, PDF path, review sheet) were exercised once with the deterministic fake through a throw-away copy of the runner with the preflight bypassed; that checks the code only and is not a model result.

## 5. Report in two parts
* **Prompt and code changes:** as above; tested against the fake provider and unit fixtures only.
* **Real-model quality results:** none. Naturalness, factual accuracy, relevance, latency and cost of real model output remain unmeasured.
