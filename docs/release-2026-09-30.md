## 3. Matching quality (full evidence: `docs/matching-evaluation.md`)

Cause: production runs the 30 August scorer. On realistic text it tops out near 48% (a near-exact "Business Analyst" match scored 48.9% locally, 48.1% in production); the current repository scorer scores it 55.7%; with this branch 59.4%. Development split: strong pairs ≥ 50%: 33% → 50% → **75%**; poor/hard pairs ≥ 50%: 6 → 17 → **0**; hard mismatches stored: 7 → 6 → **0**; NDCG@5 0.77 → 0.69 → **0.86** (deployed → repository → this branch). Held-out split: 9/10 criteria; two Azerbaijani-language noise pairs at 0.508/0.513 remain above the floor and one strong pair sits at 0.499, so the **0.50 floor is borderline for Azerbaijani-language profiles and was not moved**. The score is a suitability index, not a probability of being hired; no outcome data exists. Everything is synthetic; real-profile performance is unproven until shadow-checked with consent.

## 10. One production change plan (for your approval)

> **Corrections after the 1 October verification (this supersedes the steps below where they differ; details and evidence: `docs/cloud-handoff-2026-10-01.md`).**
> 1. **Images are built from the merged commit only**, with `scripts/build-image.sh <service> <40-char sha>` from a clean checkout. Each image records its commit in the `org.opencontainers.image.revision` label. Before step 2 and before any swap, `scripts/check-image-provenance.sh <image> <sha> [paths]` must pass for every image (and for the api image prove `dist/scripts/backfill-dedup-keys.js`, `rescore-profiles.js` and `repair-glorri-locations.js` are present). **Images built earlier (for example from `04dffd9`) must not be deployed**: they lack later fixes and scripts.
> 2. **Before the window, run the image-mode rollback rehearsal with those exact images:** `EXPECT_SHA=<sha> scripts/rehearse-rollback-compat.sh <old-api-id> <new-api-id> <new-matching-id> [<old-web-id>]` and require `ROLLBACK COMPATIBILITY REHEARSAL PASSED (docker runtime)`. The native-runtime pass (real code, no images) is not a substitute.
> 3. **Add the operator backfill after step 7** (new API running, before the importer's next hourly run): `docker compose exec api npm run script:backfill-dedup-keys:prod` (dry run, counts only), then `-- --apply`. It is guarded against the live importer and safe to repeat; the importer would also do it, 500 rows per hour.
> 4. **Replace the informal post-deploy checks of step 12 with the verifier:** `EXPECT_SHA=<sha> EXPECT_IMAGES="api=sha256:...,web=sha256:...,matching-service=sha256:..." scripts/verify-deployment.sh` (ids from `docker image inspect --format '{{.Id}}'`, as recorded by `adopt-prebuilt-images.sh`). It must exit 0: it fails closed (a stopped container, a failing `docker exec` or an unreadable value is a FAIL), checks the running image ids, the release, migrations, the scorer's token contract and self-test, payments off, live auto-apply off, the MFA key, and the importer. Then `scripts/check-host-security.sh` and `scripts/check-health.sh` as before.
> 5. **Gates (all must be true before step 1; as of this head the first two are not):** a durable company-controlled off-host backup destination verified by `offhost-sync.sh --selftest` (the Mac is not durable storage); an alert destination that a person confirmed by receiving a test alert; CI green on the exact merged head; the founder's merge; a freshly proven backup set (step 5).
> 6. **Rollback hazards to read before the window:** the previous API image tolerates the new schema (rehearsed), but it does not know the silent-rescoring marker, so matches a silent rollout created in the last 72 hours could be emailed by the old code, and it shows duplicate-linked postings again. There is no switch that pauses match emails (the only operator switches are external auto-apply and the Glorri import), so if a rollback is ever needed within 72 hours of a silent rollout, decide how to prevent those emails *before* rolling back; the rehearsal confirms the limit but does not remove it. Never restore a database backup over a system that has taken new writes.


**Boundaries.** One maintenance window of about 30–45 minutes, off-peak, with a person at `tefma` who has `sudo`.
