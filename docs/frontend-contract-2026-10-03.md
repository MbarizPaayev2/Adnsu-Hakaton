# Frontend contract for the retention and product work (3 October 2026) — living document

Owner of screens and visual treatment: the frontend worker (Gemini/Antigravity). Owner of API, schema, queues, entitlements, billing and integration: backend. This file is the contract; each section says whether the endpoint is **live in this branch** or **planned** (shape provisional until its checkpoint lands; the section is then updated with the exact DTOs). Anything shown from fixtures must be labelled as fixture data in the UI; UI readiness is not live transport verification.

Conventions: all authenticated routes use the existing session bearer token; errors are `{statusCode, message}` with Azerbaijani messages; 401 without a session, 403 for another owner's resource is reported as 404 (owner isolation never reveals existence).

## 1. Product and entitlements — LIVE (checkpoint 2)
- `GET /billing/catalogue` (public) → `{specVersion, status:'proposal', positioning:{landing:{headlineAz,subAz}, cvPreview:{az}, applicationReview:{az}, premiumComparison:{az}, finePrintAz, needsEvidenceBeforeClaiming:[…]}, candidate:{offers:[{id,label,plan,legacy,price:number|null,currency:'AZN',purchasable,features:{[key]:FeatureGrant}}], never:[…]}, employer:{offers:[… purchasable:false, unavailableReason], addons:[{id:'promoted_listing',mustBeLabelled:true,labelAz:'Promosyon',price,purchasable:false}], invariants}}`.
  `positioning` holds the approved short value copy for the landing, CV preview, application review and Premium comparison (use these strings; they say what the product does, name the candidate's review, and make no interview promise or figure; keep `finePrintAz` near any use of "Harvard"). `price: null` means "not for sale": show no price and no buy button. Never hard-code a number from this document.
- `GET /billing/entitlements` (auth) → `{specVersion, plan, offer, legacy, features:{[key]:{enabled, limit?:number|null, period?:'day'|'month'|'lifetime'|'per_match', costly?, availability?:'available'|'planned'|'disabled', note?, used?, remaining?}}}`.
  Feature keys: `discovery.public_jobs, applications.tracking, profile.cv_tools, alerts.in_app, alerts.email_digest, alerts.instant, saved.jobs, saved.searches, follows.companies, cv.versions, tailored.cv, tailored.cover_letter, preferences.rich, applications.advanced_preparation`.
  `availability:'planned'` = not built: show it as "coming", never as usable. `limit:null` = no stated limit (do not write "unlimited").
- `POST /billing/checkout-session {planId:'premium'|'basic'|'standard'|'unlimited'}` → `{url}`. 503 "Bu plan hələ satışda deyil" while the price is unset. Nothing is granted by starting checkout; the plan changes only from the signed provider webhook.
- Existing and unchanged: `GET /billing/plans` (now includes `premium` with `price:null, purchasable:false` until configured), `GET /billing/status`, `GET /billing/subscription`, `POST /billing/portal-session`.
- Copy rules: no interview/hiring promise, no "unlimited AI/auto-apply", no ATS score, no Harvard endorsement. The catalogue test fails on these phrases.

## 2. Saved jobs, saved searches, company follows — LIVE (checkpoint 3)
All routes need a session; another account's resource is reported exactly like a missing one (404 on patch, `{removed:false}` on delete). Limits come from the entitlements (`saved.jobs`, `saved.searches`, `follows.companies`); at the limit the API answers **409** "Planınızın limiti dolub. Köhnə qeydlərdən birini silin." — show the limit and `used` from `/billing/entitlements` (counts are not returned here).
- **Posting reference** `ref` = `"imported:<id>"` or `"native:<id>"` — the catalogue item's `kind` and `id`.
- `GET /saved-jobs` → `[{id, ref, kind, title, company, location|null, postedAt, deadline|null, state:'open'|'closed'|'expired', savedAt}]`. A closed or expired posting stays in the list with its state; never present it as open.
- `PUT /saved-jobs/:ref` → `{id, created:boolean}` (idempotent; a duplicate posting is saved as its canonical original, so it is the same row). 404 for hidden/closed/unknown postings, 400 for a malformed ref, 409 at the limit.
- `DELETE /saved-jobs/:ref` → `{removed:boolean}`.
- `GET /saved-searches` → `[{id, name, criteria, alertsEnabled, createdAt, updatedAt}]`.
- `POST /saved-searches {name?, criteria, alertsEnabled?}` → `{id, created}`. `criteria` may hold only the public catalogue filters `q, location, category, source, company, work, experience, sort` (strings, validated by the catalogue's own rules, defaults dropped, at least one real filter). Unknown keys, URLs, SQL-like fields or an empty search → 400. An overlapping search (same filters up to case, accents and spacing) returns the existing id with `created:false`.
- `PATCH /saved-searches/:id {name?, alertsEnabled?}` → `{id, …changed}` (404 if not yours). `DELETE /saved-searches/:id` → `{removed}`.
- `GET /company-follows` → `[{id, companyKey, companyId, displayName, createdAt}]` (`companyId` is set for registered employers; the key is `company:<id>`).
- `PUT /company-follows {companyId}` (integration checkpoint: follow a registered, APPROVED employer by its stable id; key `company:<id>`; anything else is 400/404) **or** `{company}` / `{ref}` (imported employers, by canonical name) → `{id, companyKey, displayName, created}`. One follow per canonical company (normalised name, legal suffix ignored: "Kapital Bank ASC", "kapital bank" and "KAPITAL  BANK" are one). `DELETE /company-follows/:id` → `{removed}`.
- Deleting the account removes all three (cascade). Notification behaviour for saved searches and follows arrives with section 3.

## 3. Notification preferences, new-job alerts, unsubscribe — LIVE (checkpoint 4)
Two separate event kinds: **match** events (a scored recommendation: existing in-app `NEW_MATCH` notification and batched match e-mail) and **new-job** events (a new posting that hit one of the user's saved searches with alerts on, or a followed company: in-app `NEW_JOB` notification and an alert e-mail). A new-job alert is never a fit score and the e-mail says so. Defaults reproduce today's behaviour.
- `GET /notification-preferences` → `{matchInApp, matchEmail, newJobInApp, newJobEmail:'OFF'|'DAILY'|'INSTANT', newJobTelegram:'OFF'|'DAILY'|'INSTANT', matchTelegram, instantDailyCap, quietStartMinute|null, quietEndMinute|null, pausedUntil|null, emailUnsubscribedAt|null, emailEnabled, instant:{available:boolean, dailyLimit:number|null}}`. Defaults: in-app on, match e-mail on, new-job e-mail `DAILY`, no quiet hours, no pause. Quiet hours are minutes after midnight in **Baku time** (UTC+4); a window may wrap midnight (1320 → 420 = 22:00–07:00). Telegram fields exist but stay inert while the adapter is disabled (section 4).
- `PUT /notification-preferences` with any subset of the writable fields above plus `emailEnabled:boolean` (false = unsubscribe from non-essential e-mail, true = resubscribe; only the signed-in user can resubscribe). Returns the same view. 400 (Azerbaijani message) for: unknown frequency, non-boolean flags, `instantDailyCap` outside 1–50, quiet minutes outside 0–1439 or only one of the pair or equal, `pausedUntil` not a date or more than 90 days away, and **`INSTANT` when `instant.available` is false** (Free plan). `pausedUntil:null` resumes.
- Instant alerts are bounded: at most `min(instantDailyCap, plan limit)` a day; the rest are folded into the daily digest (9:00 Baku). If the plan stops including instant, pending instant alerts move to the digest, never lost.
- What the user sees in-app: `GET /notifications` (existing) now also returns `type:'NEW_JOB'` items with `payload:{jobId, ref:'imported:<id>', searchIds, followed}`; open the posting at `/jobs/<kind>/<id>` taken from `payload.ref` (`imported:<id>` or, since the integration checkpoint, `native:<id>` for a registered employer's vacancy; the screens accept only that exact shape). Followers of a registered employer are matched by its stable company id, never by name; a new or reactivated ACTIVE native vacancy produces one alert per follower/search match.
- Unsubscribe: every alert e-mail (and now match e-mail) carries a signed link `GET /notifications/unsubscribe?token=…` (public, idempotent, 200 `{unsubscribed:true}`; 400 for an invalid token; the same 200 for a deleted account). `POST` of the same URL is the one-click form. The page behind the link is the frontend's: show a confirmation and a way to resubscribe in settings.
- Behaviour you can rely on (all tested): one alert per user and posting even with several overlapping searches/follows, retries or the same posting from two sources; closed, hidden, expired and duplicate-linked postings never alert; preferences, subscriptions and posting state are re-checked at send time; quiet hours defer (not drop); a pause or unsubscribe sends nothing; one user's transport failure does not affect others and is retried up to 5 times then marked failed.
- Local delivery uses the capturing/sink e-mail transport only. No real message is sent by any test; real sending needs the existing provider configuration and `NOTIFICATION_LINK_SECRET` (≥ 32 characters; without it alert e-mail is **not** sent).

## 4. Telegram link — LIVE in code, **DISABLED** until credentials and live verification exist (checkpoint 5)
Telegram is a notification channel only (alerts, pause, disconnect). It never accepts CVs or files (any text or file gets a fixed reply "AISE bu botda CV və ya fayl qəbul etmir"). No bot exists and nothing was sent anywhere; tests use a local capture.
- `GET /telegram` → `{enabled:boolean, status:'NOT_LINKED'|'PENDING'|'ACTIVE'|'PAUSED'|'DISCONNECTED', linkedAt|null, pausedAt|null, tokenExpiresAt|null}`. **While `enabled` is false, show the feature as "coming soon"; do not offer a connect button.**
- `POST /telegram/link-token` → `{deepLink:'https://t.me/<bot>?start=<token>', expiresAt}` (single use, expires in 15 minutes, a new call replaces the old token). 503 "Telegram bildirişləri hələ aktiv deyil" while disabled; 400 if already linked. The user opens the link in their own Telegram app.
- `POST /telegram/pause`, `POST /telegram/resume` → status view (400 if there is no active/paused link); `DELETE /telegram` → status view (`DISCONNECTED`; the chat is released). The same actions exist in the chat as `/pause /resume /stop /status`.
- Delivery preference lives in `/notification-preferences` (`newJobTelegram: 'OFF'|'DAILY'|'INSTANT'`, same bounds as e-mail). Alerts go only to an active, unpaused private-chat link; paused or disconnected means nothing is sent.
- Server-only (the UI never calls it): `POST /webhooks/telegram`, authenticated by Telegram's secret header, idempotent per update id.

## 5. Application timeline and outcomes — LIVE (checkpoint 5)
- `GET /applications/timeline` (auth) → `[{id:'email:<id>'|'native:<id>'|'external:<id>', channel, applicationId, title, company, createdAt, documentKind:'base'|'tailored'|null, stages:[{key, at|null, evidence:'SYSTEM'|'PROVIDER'|'EMPLOYER_CONFIRMED'|'CANDIDATE_REPORTED', note?}], current, problem:{key, at, evidence}|null, dryRun, nextActions:[{key, href?, note?}]}]`, newest first.
  Stage keys in order: `DRAFT, APPROVED, PROVIDER_ACCEPTED, DELIVERED, REPLY_RECEIVED, IN_REVIEW, INTERVIEW, OFFER, HIRED`. **Provider accepted ≠ delivered ≠ read ≠ employer reply**; show each as its own step and use the `note` text (E-poçt: "handed to the e-mail service; not proof of delivery or reading"). `problem.key` is one of `BOUNCED, COMPLAINED, FAILED, UNCERTAIN, CANCELLED, UNCONFIRMED, EXPIRED, REJECTED, WITHDRAWN` and is not progress.
  **Interview/offer/hired stages exist only with evidence**: `EMPLOYER_CONFIRMED` (the employer changed the status in AISE) or `CANDIDATE_REPORTED` (entered or confirmed by the candidate). Label candidate-entered ones as such ("Siz qeyd etdiniz"). A single application can show both for the same step; do not merge them. Nothing is inferred from delivery, silence or tracking.
  `dryRun:true` = a rehearsal that submitted nothing: never show it as sent. `nextActions[].key` ∈ `review_and_approve, check_before_deciding, check_recipient_address, report_outcome, wait_for_employer, check_source_site`; they are suggestions: AISE never e-mails an employer on its own.
- `POST /applications/native/:id/outcome` and `POST /applications/external/:id/outcome` `{outcome:'INTERVIEW'|'OFFER'|'HIRED'|'REJECTED'|'WITHDRAWN', occurredAt?:ISO (not in the future), note?:≤500}` → `{id, created}` (idempotent per outcome). 400 for a draft/dry-run/failed external application, 404 for another account's id. For **e-mail** applications keep using the existing `PATCH /email-applications/:id/status`.
- `GET /billing/entitlements` and the catalogue do not change. Counts of interview evidence by evidence type exist only as an operator script (`npm run script:application-outcomes`), never in a customer screen, and are counts, not rates.

## 7. Integration notes (frontend ↔ backend, checkpoint 6)
- Owner vacancy reads (`GET /business/vacancies`, `/business/vacancies/:id`) carry `_count.applications`, the authoritative count. A screen that cannot read it must treat it as **unknown** (lock question editing, show "—"), never zero. Question edits after an application exists are still refused by the backend (transaction + FK guard), so a concurrent arrival is protected server-side whatever the screen believes.
- `GET /companies` and `GET /companies/:id` count and list only ACTIVE, not-expired vacancies of APPROVED companies; a suspended company disappears from public lists and cannot receive applications or create vacancies.
- Companies have no logo field; screens render the initials mark. Uploaded assets (if ever added) must stay behind the session guard.
- Live retention adapter limits (reported through `capabilities`, not faked): no weekly digest, one e-mail cadence per account (no per-search frequency), pause = 30 days. Premium is purchasable only when the server catalogue says so *and* `/billing/status.paymentsEnabled` is true; a failed status call means "not purchasable".
- Dashboard application count and reply evidence come only from `GET /applications/timeline`; a failed request is "unavailable". Employer-confirmed, candidate-reported and system-observed evidence are shown separately; unread notifications are never presented as employer replies.
