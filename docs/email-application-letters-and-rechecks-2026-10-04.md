# E-mail applications: approved letter attachment, listing evidence and send-time rechecks — 4 October 2026

Backend checkpoint 4. It extends the existing candidate-approved pipeline (`src/email-applications/*`); nothing was rebuilt. All verification used the local fake provider/capture sink and synthetic recipients: no real message was sent, no live transport enabled.

## What was already in place (unchanged)
Explicit address only when the posting itself says where to send the CV (an ambiguous posting yields none); candidate approval bound to a SHA-256 over recipient, subject, body, attachment hash and name, reply-to, sender; private copy of the attachment taken at approval; one provider call per claim with an idempotency key; an outcome nobody can confirm is `UNCERTAIN` and is never re-sent without the candidate's explicit acknowledgement; provider acceptance, delivery, bounce and complaint are separate monotonic evidence; automatic mode needs its own consent and rules and stops on any unknown or extra requirement (including "motivation letter").

## Added
* **Approved letter as a second attachment.** `POST /email-applications/prepare { jobId, resumeId?, letterId? }`, `PATCH /:id/draft { letterId | removeLetter }`, `GET /:id/letter`. A letter must be the candidate's own, `READY` (explicitly approved), written for this very vacancy, and its file must match an `APPROVED` document snapshot (`fileSha256`), so an edited or regenerated letter can never ride on an old approval. A letter is never accepted as the CV. Automation never attaches a letter.
* **Approval bound to every byte.** Without a letter the hash is computed exactly as before (`v1`), so earlier approvals still verify. With a letter the hash (`v2`) also covers the letter's bytes and file name. At approval each file is re-read and compared with the previewed hash (`CV_CHANGED` / `LETTER_CHANGED`, nothing queued), copied privately, and at send the sender re-verifies both copies and the combined hash (`INTEGRITY_MISMATCH` otherwise). The transport now carries an `attachments` array.
* **Source evidence shown with the recipient.** The preview's `recipientEvidence` now carries `sourceUrl`, `observedAt` (the last import that saw the listing) and `listedAt` next to the posting's own excerpt.
* **Listing freshness.** A listing no import has seen for `EMAIL_APPLY_LISTING_MAX_AGE_DAYS` (default 30) is `LISTING_STALE`: not offered, not prepared, not approved, and not sent.
* **Rechecks immediately before the provider call** (in addition to the existing job open, recipient, instructions, suppression, allow-list, pause, consent and automation checks): listing freshness; another application to any listing of the same vacancy already sent or possibly sent (`DUPLICATE_APPLICATION`); the account's e-mail still verified.
* **Evidence stays separate.** `GET /email-applications/:id` returns `evidence` (provider timestamps only) and `recruitment { state, evidence, employerConfirmed }`: an outcome is `CANDIDATE_REPORTED` unless the candidate confirmed it from a reply that actually arrived at the tracking address (`REPLY_CONFIRMED_BY_CANDIDATE`, the only case `employerConfirmed` is true). A provider event can never produce an interview, offer or rejection.
* **Lifecycle of the private letter copy** follows the CV copy: removed on cancel, at retention expiry, and with the account.

## Verification
`test/email-application.e2e-spec.ts` (53 tests, 7 new): evidence with source URL and observation time; exact CV+letter bytes captured by the sink and matching their hashes; approval refused when the previewed hash no longer matches; no-letter applications unchanged; letter refused when unapproved, a CV, for another vacancy, someone else's, tampered against its snapshot or replaced after preview; stale listing at preparation and at send; duplicate-vacancy and unverified-account stops at send; private copy deletion; evidence labels. Unit: hash compatibility (`email-application-state.spec.ts`). Migration `20261017100000_email_application_letter_attachment` adds six nullable columns (fresh database verified, no drift).

## Not verified
No live provider, domain or real recipient was used; live delivery behaviour, DKIM/SPF alignment and real employer replies remain unproven. Admin plan overrides still list only the legacy plans (Plus/Premium overrides are a product decision for later).
