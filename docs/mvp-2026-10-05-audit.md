## What counts as end to end

1. Candidate registers, receives mail, verifies, uploads a supported CV, corrects parsed facts, receives relevant active jobs, generates/downloads a factual tailored CV, submits, and sees a truthful status.
2. Employer registers, receives mail, is approved through the admin UI, publishes a vacancy, receives the application and attachment, updates its status, and the candidate sees the update.
3. External application targets one supported destination. Candidate approves destination/data/notice, answers required questions, reviews and confirms, handles OTP if needed, and the destination acknowledges receipt. A cooperating recipient verifies a controlled pilot application. A local fixture alone cannot establish this final fact.
4. Founder logs in independently, approves employers, moderates jobs, inspects application/queue failures, manages permitted account actions, pauses automation, and sees auditable system status.
5. Paid launch additionally requires a completed sandbox payment/webhook/entitlement/cancellation lifecycle. A checkout URL or a database-granted test plan is not that evidence.
6. Infrastructure survives a fresh deployment and a tested restore of both database and uploaded files under company-controlled accounts.

The existing `scripts/smoke-e2e.sh` is useful API coverage, but it reads verification tokens from the database, approves the company directly and grants a test plan directly. It does not prove mailbox delivery, the admin approval UI, paid checkout or an external employer's receipt.

## Launch decision

Improve the existing system. Keep the launch scope to the journeys above, with external automation limited to a verified destination and invited pilot users. Do not buy GPU hardware, rewrite the stack, add broad multi-site auto-apply or conduct a visual rebrand as prerequisites.

“Enabled”, “build passed”, “tests mocked successfully”, “clicked submit”, and “employer received it” are different claims. Record exactly which one the evidence supports.
